# CLAUDE.md

Bu dosya, bu depoda çalışırken Claude Code'a rehberlik eder.

## Proje

YIPPEE Learning Platform — fiziksel eğitim kartlarının üzerindeki QR kod ile çalışan çocuk eğitim platformu. Kullanıcı QR'ı okutur → `play.php?t=TOKEN` → lisans doğrulanır → soru modülü yüklenir. Tam ürün spesifikasyonu için kullanıcının ilettiği "YIPPEE LEARNING PLATFORM" dokümanına bakın (bu dosyadaki mimari kararlar o spesifikasyondan türetilmiştir).

## Geliştirme Kuralı — Faz Disiplini

Bu proje `ROADMAP.md` içinde tanımlı fazlar halinde geliştirilir. **Bir faz tamamen bitmeden, kod kontrol edilip hatalar düzeltilmeden, gerekli migrationlar hazırlanmadan, test edilmeden, README ve CHANGELOG güncellenmeden ve kullanıcı onayı alınmadan bir sonraki faza geçilmez.** Aksi açıkça istenmedikçe bu kurala uyulmalıdır. Güncel faz durumu için `ROADMAP.md` dosyasına bakın.

## Teknoloji

- Backend: PHP 8.3, MySQL 8, custom MVC (framework yok, Composer sadece PSR-4 autoload için)
- Frontend: Bootstrap 5 (CDN), HTML5, CSS3, Vanilla JavaScript (ES2023) — **jQuery kullanılmaz**
- Kütüphaneler (CDN üzerinden, build adımı yok): QRCode.js (admin panelde QR görüntüleme), GSAP (oyun ekranı animasyonları), Howler.js (`AudioManager`, bkz. aşağıda). Chart.js henüz entegre edilmedi — dashboard istatistikleri (Faz 14) gerçek ihtiyaç doğduğunda eklenecek (YAGNI).
- Oyun ekranı fontu Google Fonts "Baloo 2" (CDN) — sadece `play.php` sayfalarında, admin panel Bootstrap'in sistem fontunu kullanmaya devam ediyor.

## Mimari — Katmanlar

MVC + Repository Pattern + Service Layer. PSR-12, SOLID, DRY hedeflenir.

```
Controller → Service → Repository (interface) → Model (table gateway) → Database (PDO)
```

- **Model** (`app/Models/*`): `BaseModel`'den türer, ham PDO CRUD sağlayan tablo gateway'i (`all/find/where/create/update/delete`). Settings gibi `id`+auto-increment şemasına uymayan tablolarda Model kullanılmaz, Repository doğrudan `Database::connection()` ile PDO'ya konuşur.
- **Repository** (`app/Repositories/*`, arayüzler `app/Repositories/Contracts/*`): Domain'e özel sorgu/yazma metodlarını tanımlar (ör. `LicenseRepositoryInterface::findByToken()`), Model çağrılarını sarar. Service'ler somut Repository değil, **interface**'e bağımlı olur (DIP).
- **Service** (`app/Services/*`): İş kuralları burada yaşar (şifre doğrulama, token/kod üretimi, lisans durum hesaplama, aktivasyon takibi). Kural ihlalinde `App\Services\Exceptions\ValidationException` fırlatır; controller bunu yakalayıp `Session::flash('error', $e->getMessage())` yapar. Yeni bir domain kuralı eklerken controller'a değil, ilgili Service'e yazın.
- **Controller** (`app/Controllers/*`): Yalnızca HTTP orkestrasyonu — request okuma, CSRF doğrulama, Service çağırma, redirect/view. İş kuralı içermez.

Mevcut örnek: `AuthService` (login/logout/şifre değiştirme), `LicenseService` (lisans oluşturma/durum/aktivasyon takibi), `SettingService` (site URL, varsayılan süre/puan/can gibi tekil ayarlar), `CategoryService` (kategori CRUD + silme koruması), `QuestionService` (soru+4 seçenek+medya birlikte yönetimi), `StartScreenService` (başlangıç ekranının admin-yönetilebilir metin/görselleri), `GameSessionService` (sunucu-taraflı oyun oturumu — bkz. Oyun Motoru bölümü).

## Diğer Çekirdek Kurallar

- **Front controller**: Tüm istekler kök dizindeki `index.php`'ye düşer (`.htaccess` rewrite ile). `public/` klasörü yok — `DocumentRoot` proje kökünü gösteriyor, bu yüzden `app/`, `config/`, `routes/`, `storage/`, `database/` klasörleri kendi `.htaccess` dosyalarıyla ve kök `.htaccess`'teki `RewriteRule ... [F,L]` kuralıyla web erişimine kapatılmış durumda. Yeni bir "gizli" klasör eklerken bu korumayı unutmayın.
- **Routing**: `routes/web.php` bir `App\Core\Router` örneği döndürür. `$router->get()/post()` ile route tanımlanır, `{param}` segmentleri controller metoduna pozisyonel argüman olarak geçer.
- **View**: `App\Core\View::render()` nokta notasyonu kullanır (`admin.login` → `app/Views/admin/login.php`). Varsayılan layout `layouts/main.php` (public sayfalar) veya `layouts/admin.php` (admin panel, Bootstrap navbar içerir); `render($view, $data, null)` ile layout'suz render edilebilir (`play.php`'nin kendi tam HTML döküman view'ları gibi).
- **Config/Env**: `.env` dosyası `App\Core\Env` ile okunur, `config/*.php` dosyaları `App\Core\Config` ile yüklenir. Kod içinde `env()` değil, `config()` helper'ı tercih edilmeli (env sadece config dosyaları içinde kullanılır). Admin panelden değiştirilebilen değerler (ör. site URL) `config()`'te değil, `settings` tablosunda (`SettingService`) tutulur.
- **Global helper fonksiyonları** `app/Core/helpers.php` içinde tanımlı ve composer'ın `autoload.files` ile otomatik yüklenir: `config()`, `env()`, `base_url()`, `asset()`, `e()` (XSS-safe escape), `csrf_field()`, `dd()`.
- **Session/Auth**: `App\Core\Session` genel session işlemlerini (get/put/flash/csrf) sağlar; `App\Core\Auth` bunun üzerine admin kimlik doğrulama semantiğini (`login()/logout()/check()/user()`) katar. `index.php` `Session::start()` çağırır — ham `session_start()` kullanmayın.
- **Admin route koruması**: Giriş gerektiren admin controller'ları `App\Controllers\Admin\AdminBaseController`'dan türetilir; constructor `Auth::check()` değilse `/admin/login`'e yönlendirir ve `$this->admin` dizisini doldurur. Herkese açık admin route'ları (login/logout) düz `BaseController`'dan türetilir.
- **CSRF**: State değiştiren tüm POST formlarında `<?= csrf_field() ?>` kullanılmalı, controller tarafında `Session::verifyCsrf($request->input('_csrf'))` ile doğrulanmalı.
- **Migration**: `database/migrations/*.php` her biri `App\Core\Migration`'ı extend eden anonim bir sınıf döndürür (`up(PDO)/down(PDO)`). Dosya adı `YYYY_MM_DD_HHMMSS_aciklama.php` formatında olmalı (sıralama buna göre yapılır). Şema değişikliği gerektiğinde **mevcut migration dosyasını değiştirmeyin** — zaten çalıştırılmış olabilir; yeni bir `ALTER TABLE` migration'ı ekleyin (örnek: `2026_07_28_120000_add_details_to_licenses_table.php`). Çalıştırmak için `php database/migrate.php migrate`, geri almak için `php database/migrate.php rollback` (son batch'i geri alır).
- **play.php**: Roadmap'te ayrı bir dosya olarak belirtildiği için kök dizinde, router'dan bağımsız bir giriş noktası olarak tutuluyor (`index.php` ile aynı bootstrap deseni: autoload + `Env::load` + `Config::load` + artık `Session::start()`). Query parametresi `t` (spec'te böyle: `play.php?t=TOKEN`) — `token` değil. Doğrulama/takip mantığı `LicenseService::validateAndTrack()` içinde; `ValidationException` mesajı doğrudan kullanıcıya gösterilir. Başarılı doğrulamada `Session::put('play_authorized', true)` ile `/play/api/*` uçlarının kullanımı yetkilendirilir, sonra `play.index` view'ı (başlangıç/oyun/sonuç ekranlarının hepsini içeren tek sayfa kabuk) render edilir. Gelecekte oyun motoru mantığı büyürse bile bu dosyayı router'a taşımayın — kasıtlı bir mimari karar; asıl oyun API'leri (`/play/api/*`) normal router üzerinden `GameController`'a gider, sadece token doğrulama girişi standalone kalıyor.
- **Lisans/QR**: Sistem token + lisans kodu (`code`, insan-okunur, `Str::code()`) üretir. QR görseli **istemci tarafında** QRCode.js ile admin panelde (`admin/licenses/index.php` → QR modal, `assets/js/license-qr.js`) üretilir — PHP tarafında QR kütüphanesi yok. Oynama linki `{site_url}/play.php?t={token}` şeklinde, `site_url` admin panelden değiştirilebilir (`SettingService::getSiteUrl()`, `.env`'teki `APP_URL`'e fallback yapar). Lisans durumu (`Aktif/Pasif/Süresi Doldu`) DB'de ayrı bir alan olarak tutulmaz, `LicenseService::statusLabel()` ile `is_active` + `expires_at`'ten hesaplanır (stale veri riskini önler). Her `play.php` doğrulamasında `first_activated_at` (ilk kez), `last_used_at`, `last_ip`, `last_device` güncellenir.
- **Soru Modülü**: "Soru Modülü Sistemi" ilkesi — her soru (`questions` + tam olarak 4 `question_options` satırı, pozisyon A/B/C/D) tamamen bağımsız, birbirine referans vermez. `duration_seconds`/`points` alanları **nullable**: `NULL` = Site Ayarları'ndaki varsayılanı miras al (`SettingService::getDefaultDuration()/getDefaultPoints()`), dolu değer = soru bazında istisna. Bu "genel varsayılan → ayarlar, istisna → soru" deseni yeni benzer alanlar eklerken de takip edilmeli. Kategori silme, o kategoriye bağlı soru varsa `CategoryService::delete()` içinde engellenir (DB'de de FK `RESTRICT` ile ikinci bir güvenlik katmanı var).
- **Medya yükleme**: `App\Services\MediaUploadService` görsel (webp/png/jpg, ≤5MB) ve ses (mp3/ogg, ≤10MB) dosyalarını doğrular, `config('app.uploads_path')` (= proje kökü `uploads/`) altına `{questions|options}/{id}/{slot}.{ext}` şeklinde sabit-slot isimlendirmeyle kaydeder. Yeni dosya yüklendiğinde eski dosya (farklı uzantıda olsa bile, DB'deki kayıtlı yoldan) otomatik silinir; "kaldır" checkbox'ı işaretlenip yeni dosya yüklenmezse dosya silinir ve DB alanı `NULL` yapılır. `uploads/` kökteki `.htaccess` ile PHP/script çalıştırma engellenmiştir ama statik dosya olarak `base_url($question['card_image'])` gibi doğrudan servis edilir (assets/ ile aynı mantık, `storage/`'dan farklı olarak **web'e açık**). `$_FILES['options'][...]` PHP'nin nested-file-input tuhaflığı yüzünden `QuestionService::normalizeOptionFiles()` ile düzleştirilir — yeni bir nested file input eklerken bu deseni tekrar kullanın.

## Oyun Motoru (Faz 5)

Katmanlar net ayrılmış: **istemci** `GameEngine` sınıfı (`assets/js/game-engine.js`, DOM'a hiç dokunmaz, sadece state + `fetch` çağrıları + `AudioManager` API çağrıları) ve **sunucu** `App\Services\GameSessionService` (PHP session'da oturum durumunu tutar, doğru cevabı asla istemciye göndermez). Ayrı bir `assets/js/game-ui.js` bu ikisini DOM'a bağlar (render, GSAP animasyonları, timer, buton olayları). Yeni oyun mantığı eklerken bu üçlü ayrımı bozmayın — UI dosyasına state/skor hesaplama, engine dosyasına DOM/`document.*` sızdırmayın, hiçbir dosyada doğrudan `new Howl()` çağırmayın (bkz. AudioManager bölümü).

- **Oturum durumu**: `GameSessionService` PHP `$_SESSION['game']` içinde soru ID sırasını (`sort_order`'a göre tüm aktif sorular — lisans artık kategoriye bağlı değil), mevcut index, skor, can, o anki soruda denenmiş şıkları (`attempted`) ve `game_over` bayrağını tutar. Doğru cevap kontrolü sunucuda yapılır (`is_correct` hiçbir zaman JSON'a sızdırılmaz); istemci sadece `position` gönderir.
- **API uçları** (`App\Controllers\GameController`, normal router üzerinden, admin auth'u yok): `POST /play/api/start`, `POST /play/api/answer` (`position`), `POST /play/api/timeout`. Her biri `guardAuthorized()` (play.php'de set edilen `play_authorized` session flag'i, yoksa 403) ve `guardCsrf()` (`Session::verifyCsrf`, yoksa 419) ile korunur.
- **"Bir sonraki soru"**: `answer()` doğru cevapta cevabın sonucunu VE bir sonraki sorunun tam verisini tek response'ta (`next` alanı) döndürür — ayrı bir "get next question" ucu yok. Bu, "her geçişte yeni soru servis katmanından getirilecek, tüm sorular belleğe alınmayacak" kuralını tek round-trip'le sağlar.
- **Önceki/Sonraki (inceleme modu)**: Sunucuya gitmez — `GameEngine.history[]` istemci tarafında, tamamlanan her soru cevaplanırken zaten biriktirilir (yeniden fetch gerekmez). `viewIndex` null ise "canlı" mevcut soru gösterilir; değilse `history[viewIndex]` salt-okunur (butonlar disabled, doğru/yanlış işaretli) render edilir. Yeni bir "geçmişi sunucudan çek" ucu eklemeyin — mimari kasıtlı olarak istemci-taraflı tutuluyor.
- **Yanlış cevap / tekrar deneme**: Bir şık yanlış işaretlenince o şık `is-disabled` olur ama diğerleri (denenmemiş) tıklanabilir kalır (`attempted[]` state'i bunu sürdürür). Can küresel oyun boyunca paylaşılır (soru başına sıfırlanmaz) — 0'a inince `game_over=true`, hangi denemede olursa olsun oyun biter.
- **Süre aşımı**: `timeout()` çağrısı `answer(null, isTimeout: true)` ile aynı "yanlış" yolunu izler, sadece hiçbir şık `attempted`'e eklenmez (hiçbiri tıklanmadığı için).
- **Timer düşük-süre state'i**: `startTimer()` hem başlangıçta (ilk `seconds` değerine göre) hem her tick'te `classList.toggle('is-low', timeLeft <= 5)` yapar. Sadece interval içinde kontrol etmeyin — kısa süreli (≤5sn) sorularda ilk tick'e kadar (1sn) geç kalır, Playwright ile bu regresyon tespit edildi.
- **Başlangıç ekranı özelleştirme**: `App\Services\StartScreenService` + `/admin/settings/start-screen` — tüm görseller (`start_*_image` anahtarları, `settings` tablosunda) ve üç metin alanı (`start_title/description/button_text`) admin panelden yönetilir. Kod içinde **sabit görsel yolu veya metin kullanılmaz**; görsel ayarlanmamışsa ilgili `<img>` gizlenir ve yerine `.image-placeholder` (nötr ikon kutusu) gösterilir — kırık görsel ikonu asla görünmez. Yeni bir dekoratif görsel alanı eklerken bu deseni tekrar kullanın (`StartScreenService::IMAGE_FIELDS`'e ekleyin, view'da conditional render + placeholder div). Aynı placeholder deseni oyun ekranındaki kart/seçenek görselleri için de kullanılıyor (`#card-image-placeholder`, `#option-{X}-placeholder`).
- **Varsayılan can sayısı**: `SettingService::getDefaultLives()` (varsayılan 3), `/admin/settings` üzerinden değiştirilebilir — süre/puan ile aynı desende.
- **Playwright doğrulaması**: Bu proje için tarayıcı otomasyonu yerleşik değil, ama gerektiğinde Laragon'un `C:/laragon/bin/nodejs/node-v22` altındaki Node.js'i kullanıp scratchpad'de geçici bir `npm install playwright && npx playwright install chromium` ile kurulabilir (bkz. Faz 5/6 kapanış doğrulamaları). Kalıcı bir bağımlılık değildir, projeye eklenmedi.

## AudioManager (Faz 6)

**Tek giriş noktası**: `assets/js/audio-manager.js`, `window.AudioManager` singleton'ı olarak yüklenir (Howler.js'den hemen sonra, `game-engine.js`'den önce — `play/index.php`'deki script sırası önemli). **Uygulamanın hiçbir yerinde doğrudan `new Howl()` çağrılmaz** — yeni bir ses ihtiyacı doğduğunda bile bu kurala uyun, her zaman `window.AudioManager.play(url, { category, priority? })` kullanın.

- **İki kanal**: "main" kanalı (`card/question/option/correct/wrong/transition/badge` kategorileri — aynı anda yalnızca BİR tanesi çalar, `#main` tek slot) ve "ui" kategorisi (arayüz sesleri, main'i bloklamaz, kendi `#uiPlaying` Map'inde bağımsız takip edilir).
- **Öncelik/kesme kuralı**: Yeni istek `priority >= mevcut main'in priority'si` ise mevcut ses 180ms fade-out ile kesilir ve yenisi hemen çalar; **yalnızca kesinlikle düşük öncelikli** istekler sıraya (`#queue`, priority'ye göre sıralı) alınır. Bunun bilinçli bir tasarım kararı olduğunu unutmayın: eşit öncelik de keser — çünkü kullanıcının yeni bir tıklaması (ör. farklı bir hoparlör butonu) her zaman daha taze niyeti temsil eder; sessizce sıraya atılırsa kafa karıştırıcı olur. Kategori varsayılan öncelikleri `AudioManager` içindeki `#DEFAULT_PRIORITY`'de (card/question/option=5, transition=6, correct/wrong=8, badge=10, ui=3).
- **Aynı sesin üst üste binmesi engellenir**: Bir url zaten çalıyorsa aynı url için yeni `play()` isteği yok sayılır (idempotent); zorla yeniden başlatmak için `replay(url)` kullanın (`restart:true`).
- **Preload/Cache birleşik**: `#cache` (`Map<url, Howl>`) — `preload(url)` ve `play(url)` aynı cache'i kullanır, aynı ses ikinci kez istendiğinde yeniden indirilmez. `isCached(url)`, `unload(url)`, `unloadAll()` introspection/temizlik için var.
- **GameEngine entegrasyonu (minimum)**: `GameEngine` constructor'ı opsiyonel `audioManager` alır (`game-ui.js` içinde `window.AudioManager` geçirilir). `playCardAudio()/playQuestionAudio()/playOptionAudio(position)` — sırasıyla mevcut sorunun `cardAudio/questionAudio/options[x].audio` alanını (DB'den gelen gerçek yol, kod içinde sabit yol yok) `AudioManager.play()` ile çalar. Yeni bir soru set edildiğinde (`#applyPayload`, `#handleAnswerResult`) `#preloadCurrentAudio()` otomatik tetiklenir — kart/soru/4 seçenek sesi önceden yüklenir. `game-ui.js`'deki `#btn-question-audio` ve `.option-audio-btn` click handler'ları artık `engine.playQuestionAudio()`/`engine.playOptionAudio(position)` çağırır; ne UI ne engine dosyasında ham `Audio`/`Howl` nesnesi yok.
- **Bağlı kategoriler**: `correct/wrong/badge` Faz 7'de, `transition` Faz 7 sonrası ayrı bir modülde bağlandı (bkz. aşağıdaki "Geçiş Mesajları" bölümü) — artık 8 kategorinin tamamı en az bir yerde kullanılıyor.
- **Mute**: `mute()/unmute()/toggleMute()/isMuted()` doğrudan `Howler.mute()`'a sarar (global, tüm sesleri etkiler). `game-ui.js`'deki mute butonları artık yalnızca ikon değiştiren yerel bir `muted` değişkeni değil, gerçekten `AudioManager.toggleMute()` çağırıyor; `localStorage` sadece sayfa yenilendiğinde son tercihi hatırlamak için.
- **Mobil unlock**: `prime()` "Başla" butonuna tıklanınca çağrılır (`Howler.ctx.resume()`) — tarayıcıların "kullanıcı etkileşimi olmadan ses çalınamaz" kısıtını erken açar. Howler zaten kendi unlock mekanizmasına sahip; `prime()` sadece garantiye alır.
- **Test**: `getState()` metodu introspection için var (`{ main: {url,category,priority,playing}, queue, uiActive, muted, volume, cacheSize }`) — gerçek ses duyulmadan Playwright/konsoldan davranış doğrulanabilir. Test için gerçek MP3/OGG dosyası yoksa Node ile ham WAV üretip (`fs.writeFileSync` + RIFF header) `uploads/` altına geçici koyup DB'ye elle yazmak (admin upload validasyonunu bypass ederek) makul bir QA tekniğidir — kalıcı test verisi olarak bırakmayın, işiniz bitince temizleyin.

## Puan, Başarı Mesajları ve Rozet Sistemi (Faz 7)

Üç bağımsız sistem — ayrı Service'ler, ayrı tablolar, birbirlerine doğrudan bağımlı değiller. Yalnızca `GameSessionService` her üçünü tek bir cevap olayında orkestre eder (`answer()` içinde: puan güncelle → mesaj seç → rozet değerlendir → hepsini tek JSON response'ta döndür).

- **Puan**: Ayrı kod gerektirmedi — Faz 4'ten beri var olan soru bazlı `points` alanı zaten bu deseni uyguluyor (`GameSessionService::answer()`, doğru cevapta `state['score'] += $points`, yanlışta hiç dokunulmaz).
- **Başarı Mesajları**: `achievement_messages` tablosu (`type` ENUM correct/wrong, title, audio, animation_type, is_active). `App\Services\AchievementMessageService::pickRandom(string $type)` o gruptan **aktif** bir mesajı `array_rand()` ile rastgele seçer; hiç aktif mesaj yoksa `null` döner ve frontend sabit fallback metne düşer (`'Harika!'`/`'Tekrar Dene'`) — admin panelinden hiç mesaj girilmese bile oyun bozulmaz.
- **Rozet — genişletilebilir koşul motoru**: `badges` tablosunda her rozet bir `condition_type` (string, ör. `correct_count`) ve opsiyonel `condition_value` (int) taşır. `App\Services\BadgeService`'in constructor'ında `condition_type => closure` haritası (`#evaluators`) var; her closure `(array $context, ?int $value): bool` imzasında. **Yeni bir koşul türü eklerken:** (1) `BadgeService::CONDITION_*` sabiti + `CONDITION_LABELS`'e Türkçe etiket, (2) constructor'daki haritaya bir closure, (3) gerekiyorsa `VALUE_REQUIRED` listesine ekleyin (sayısal değer zorunluysa). Mevcut rozetler, `GameSessionService` entegrasyonu ve admin formu **değişmeden** çalışmaya devam eder — bu "kod içine sabit yazılmayan kural" gereksinimini karşılıyor.
- **Değerlendirme bağlamı (`context`)**: `GameSessionService::evaluateBadges()` her cevaptan sonra `{correctCount, score, lives, maxLives, timeoutOccurred, isFinished, gameOver}` inşa eder — `correctCount` aslında `state['index']` (doğru cevapla artan sayaç, ayrı bir alan tutmaya gerek yok), `flawless` `lives === maxLives`'tan türer (ayrı "hata sayısı" alanı yok). Yeni bir koşul türü mevcut context anahtarlarıyla ifade edilemiyorsa, önce `evaluateBadges()`'e yeni bir context alanı eklemeniz gerekebilir.
- **GameEngine yalnızca sonucu alır**: Rozet koşulu hiçbir zaman istemcide değerlendirilmez. `GameSessionService::answer()` → `evaluateBadges()` → `BadgeRepository::activeBadges()` üzerinden döner, sonuç `earnedBadges` JSON alanında (id/title/description/image/audio/animationType, tam formatlanmış) API response'una girer. `GameEngine.#handleAnswerResult()` bunu `this.badges` dizisine biriktirir (oturum boyunca, sonuç ekranı özeti için) — GameEngine'de `condition_type` kelimesi bile geçmez.
- **Tekrar verilmeme**: Session state'te `awarded_badge_ids` (int dizisi). `evaluateNewlyEarned($context, $alreadyAwardedIds)` bu listedeki id'leri atlar; her yeni kazanımda `GameSessionService` bu diziye ekler ve `Session::put()` ile kalıcı hale getirir. `start()` her yeni oyunda bu diziyi sıfırlar.
- **Ne zaman değerlendirilir**: Her doğru VE her yanlış cevaptan sonra (yanlışta yalnızca `game_over` anındaki koşullar — ör. gelecekte eklenebilecek bir "en az bir yanlış yap" rozeti — tetiklenebilsin diye; mevcut koşul tiplerinden hiçbiri yanlış dalında gerçek bir rozet üretmez ama mimari buna açık). Tamamlanma-bazlı koşullar (`flawless_completion`, `no_timeout_completion`) `isFinished=true` olduğu ana kadar hiçbir zaman `true` dönmez — sonuç ekranına geçmeden hemen önceki cevap olayında değerlendirilirler, ayrı bir "oyun bitti" tetikleyicisi yok.
- **Frontend**: `game-ui.js` `reactToAnswer()` artık `result.message?.title` kullanıyor (yoksa sabit fallback), mesaj sesi `AudioManager` `correct`/`wrong` kategorisiyle çalınıyor, `result.message?.animationType` bir GSAP tween'e eşleniyor (`ANIMATIONS` haritası: bounce/pulse/shake/pop/fade — yeni bir tip eklerken hem `App\Services\AnimationTypes::OPTIONS` hem bu haritaya ekleyin, ikisi senkron kalmalı). Rozet kazanımı `.badge-toast` elemanıyla bildirilir (`badge` kategorisiyle ses — AudioManager'da öncelik=10, yani çalmakta olan doğru/yanlış sesini keser), birden fazla rozet aynı anda kazanılırsa 1600ms arayla sırayla gösterilir. Sonuç ekranındaki `#result-badges` oturum boyunca `engine.badges`'i render eder, hiç rozet kazanılmadıysa gizlenir.
- **Medya**: Mesaj sesi ve rozet görsel/sesi `MediaUploadService` ile aynı desende yükleniyor (`messages/{id}/`, `badges/{id}/` alt klasörleri) — Faz 4'teki soru medyasıyla birebir aynı yükleme/değiştirme/kaldırma mantığı.

## Geçiş Mesajları (Faz 7 sonrası ek modül)

Faz 7'nin orijinal taslağında vardı ama o fazın kapsamına dahil edilmemişti; ayrı bir modül olarak eklendi. Yapı, dördüncü bağımsız bir sistem olarak Puan/Başarı Mesajları/Rozetler'in yanına oturur — `achievement_messages` ile birebir aynı deseni izler ama tek grup (Doğru/Yanlış ayrımı yok).

- `transition_messages` tablosu (title, audio, animation_type, is_active) + `App\Services\TransitionMessageService::pickRandom()` — aktif mesajlardan `array_rand()` ile rastgele seçim, hiç aktif mesaj yoksa `null` (frontend'de toast hiç gösterilmez, oyun bozulmaz). `/admin/transition-messages` CRUD, `AchievementMessageController`/`BadgeController` ile aynı controller/view deseninde.
- **`GameSessionService::answer()` entegrasyonu**: yalnızca doğru cevap dalında, `isFinished` **false** ise (yani sıradaki bir soru varsa) yanıta `transitionMessage` eklenir; son soru cevaplandığında (`isFinished=true`) `null` döner — geçilecek "sıradaki" soru olmadığı için mantıksal olarak doğru. Yanlış cevap yanıtında bu alan hiç yok.
- **Frontend**: `game-ui.js` `reactToAnswer()` içinde, doğru cevap animasyonundan ~700ms sonra `showTransitionToast()` çağrılır (`.transition-toast` — mor renkli, `.badge-toast`'tan görsel olarak ayrı, `assets/css/game.css`). Ses `AudioManager.play(url, { category: 'transition' })` ile çalınır; `transition` önceliği (6) `correct/wrong` önceliğinden (8) düşük olduğu için mevcut doğru-cevap sesini kesmez, doğal olarak sıraya girer/ardından çalar.
- GameEngine'de geçiş mesajı seçim mantığı yok — `submitAnswer()` API yanıtını olduğu gibi taşır, `game-ui.js` yalnızca `result.transitionMessage` alanının var/yok olduğuna bakar.

## Frontend

- Bootstrap 5 CSS/JS bundle her iki layout'ta (`layouts/main.php`, `layouts/admin.php`) CDN üzerinden yüklü — build adımı, npm, bundler yok.
- Vanilla JS dosyaları `assets/js/` altında, sayfaya özel `<script>` etiketiyle ilgili view'da dahil edilir (global bir bundle yok). Örnek: `assets/js/license-qr.js` (admin), `assets/js/game-engine.js` + `assets/js/game-ui.js` (oyun ekranı).
- jQuery kesinlikle kullanılmaz — DOM işlemleri için native API (`document.querySelector`, `addEventListener`, `dataset`, vb.). ES2023 özellikleri (private class field `#x`, `EventTarget` genişletme, optional chaining) serbestçe kullanılabilir.
- `assets/css/app.css` admin/public sayfalar için — yalnızca Bootstrap'in kapsamadığı minik override'lar. `assets/css/game.css` ise `play.php`'nin özel tasarımı için ayrı bir dosya (Bootstrap sadece grid/`row`/`col-6` için kullanılıyor, görsel dil tamamen özel CSS ile — referans tasarıma sadakat gerektiği için admin paneliyle paylaşılmıyor).

## Güvenlik

- View'larda kullanıcı girdisi veya veritabanından gelen veri basılırken her zaman `e()` helper'ı ile escape edin.
- SQL sorgularında her zaman prepared statement / named parameter kullanın (`BaseModel` ve repository'ler zaten bunu sağlıyor).
- `storage/`, `app/`, `config/`, `routes/`, `database/` klasörleri web'den erişilemez olmalı — yeni bir alt klasör eklerken kök `.htaccess`'teki `RewriteRule` listesine eklemeyi unutmayın.

## Test

Yerleşik bir test suite henüz yok (ilerleyen fazlarda eklenebilir). Değişiklik sonrası manuel doğrulama için:

```bash
composer install
php database/migrate.php migrate
```

ve `http://ingilizce.test/` ile `http://ingilizce.test/health` adreslerini kontrol edin (health endpoint DB bağlantısını da doğrular). Admin panel akışlarını (giriş, lisans oluşturma, `play.php?t=...`, soru+medya CRUD) gerçek `ingilizce.test` vhost'u üzerinden cookie jar ile uçtan uca test edin — PHP built-in server (`php -S`) `.htaccess` işlemediği için statik dosya/engelleme davranışını yanlış yansıtır. Dosya yükleme akışlarını test ederken `curl -F "field=@dosya;type=..."` (multipart) kullanın; nested option dosyaları için `-F "options[A][image]=@..."` sözdizimi çalışır.
